# 技术栈选择原因

> 创建日期: 2026-05-31
> 用途: 面试讲解时说明每个技术选型的理由

---

## 一、数据库: PostgreSQL (而非 SQLite)

### 选择 PostgreSQL 的原因

1. **生产级并发支持**: 招聘系统未来可能多人同时使用，SQLite 不支持并发写入，PostgreSQL 的 MVCC 机制天然支持高并发
2. **向量扩展**: PostgreSQL 有 pgvector 扩展，可以和 Qdrant 互补，做混合检索
3. **LangGraph 官方支持**: LangGraph 的 PostgresSaver 是官方推荐的持久化方案，支持工作流中断恢复
4. **JSONB 支持**: JD Profile 和 Candidate Profile 本身就是 JSON，PostgreSQL 的 JSONB 类型可以高效存储和查询半结构化数据
5. **校招面试加分**: 面试官看到你了解 PostgreSQL vs SQLite 的区别，说明有生产意识

### 不选 SQLite 的原因
- 不支持并发写入
- 没有原生的 JSONB 索引
- LangGraph 的 SqliteSaver 是实验性的

---

## 二、向量数据库: Qdrant (而非 Chroma / FAISS)

### 选择 Qdrant 的原因

1. **过滤能力**: Qdrant 的 payload filtering 非常成熟，可以高效按 `candidate_id` 过滤检索结果 —— 这是 RAG 证据检索的核心需求
2. **高性能**: Rust 编写，单机可处理百万级向量
3. **生产就绪**: 有 Docker 镜像、健康检查、监控接口
4. **量化索引**: 支持 Scalar/Binary Quantization，内存占用更低

### 不选 Chroma 的原因
- Chroma 适合 MVP 快速原型，但大规模下性能和稳定性不如 Qdrant
- 过滤能力较弱

### 不选 FAISS 的原因
- 纯内存/文件，没有服务端
- 不支持 payload filtering
- 不适合多服务共享

---

## 三、LLM 层: Local + Cloud 双模式

### 架构设计

```text
llm_mode = "local"  → LM Studio (http://localhost:1234/v1)
llm_mode = "cloud"  → DeepSeek API (OpenAI 兼容)
```

### 为什么这样设计

1. **开发体验**: 调试阶段用本地 LM Studio，免费、无需网络、响应快
2. **生产切换**: 部署时切到 DeepSeek API，获得更强的模型能力
3. **统一接口**: 两者都是 OpenAI 兼容 API，代码零切换成本，只改 base_url 和 api_key
4. **成本控制**: DeepSeek 比 OpenAI 便宜 90%+，中文理解能力不输 GPT-4

### 不选纯 OpenAI 的原因
- 成本高 ($15+/M tokens vs DeepSeek ~$1/M tokens)
- 国内访问可能不稳定

### 不选纯 Anthropic Claude 的原因
- Claude API 国内访问困难
- 不支持 OpenAI 兼容接口，切换成本高

---

## 四、Embedding 模型: 同样 Local + Cloud 双模式

### 架构设计

```text
embedding_mode = "local"  → LM Studio 本地 embedding 模型
embedding_mode = "cloud"  → DeepSeek Embedding API
```

### 为什么

理由和 LLM 一样 —— 开发免费、部署切换零成本。

---

## 五、结构化输出: LangChain with_structured_output

### 选择原因

1. **与 Pydantic 深度集成**: 直接传 Pydantic Model 类，LangChain 自动生成 JSON Schema 并注入 prompt
2. **自动验证**: 返回值直接是 Pydantic 实例，无需手动 JSON → dict → Pydantic 转换
3. **错误重试**: LangChain 内置了 OutputParserException 处理和自动重试逻辑
4. **模型无关**: 同一套代码，不管底层是 OpenAI/DeepSeek/LM Studio 都能用

### 不选手动 Function Calling 的原因
- 需要手动定义 tool schema
- 需要手动解析 tool_call 返回值
- 错误处理代码量大

### 不选 JSON Mode 的原因
- JSON Mode 只保证输出是合法 JSON，不保证符合你的 Schema
- 没有 Pydantic 自动验证

---

## 六、PDF 解析: LangChain Document Loaders

### 选择原因

1. **统一接口**: LangChain 的 document loaders 封装了 PyMuPDF、pdfplumber、Unstructured 等多种后端，切换只需改 import
2. **自动 metadata**: 自动注入 source、page 等元数据
3. **与 Splitter 联动**: LangChain Document 对象可以直接喂给 RecursiveCharacterTextSplitter

### 不选直接调用 PyMuPDF/pdfplumber 的原因
- 需要手动处理元数据
- 需要手动适配不同的切分器接口
- LangChain 的封装已经够用

---

## 七、文本切分: RecursiveCharacterTextSplitter

### 选择原因

1. **智能边界**: 按 `\n\n` → `\n` → ` ` → `""` 的顺序递归尝试切分，尽量保持段落/句子的完整性
2. **LangChain 原生**: 和 Document Loaders 无缝衔接
3. **后续升级**: 可以先跑起来，后面升级为 Semantic Chunking (基于 embedding 相似度判断切分点)

### 不选固定窗口切分的原因
- 可能在句子中间切断，影响 embedding 质量
- 丢失上下文连贯性

---

## 八、LangGraph 持久化: PostgresSaver

### 选择原因

1. **官方推荐**: LangGraph 团队推荐的生产级 Checkpointer
2. **中断恢复**: 工作流在 Human Review 节点暂停后，可以从数据库恢复
3. **多轮面试**: 面试辅助工作流可能需要跨天进行，必须持久化
4. **审计追踪**: 所有工作流执行历史都存在 PostgreSQL 中，方便排查问题

### 不选 MemorySaver 的原因
- 重启丢失，不适合任何需要中断的场景
- 无法支持 Human-in-the-loop

---

## 九、配置管理: Pydantic Settings

### 选择原因

1. **类型安全**: 配置写错类型 (如 CHUNK_SIZE="abc") 会在启动时直接报错
2. **自动读取环境变量**: 不需要手动 os.getenv() 每个变量
3. **.env 文件支持**: 开发用 .env，部署用环境变量
4. **嵌套配置**: 可以把 LLM、Database、Qdrant 配置分组管理

### 不选 os.getenv() 的原因
- 缺少类型验证
- 缺少默认值管理
- 配置分散在多个文件，不好维护

---

## 十、前端: Next.js + Tailwind CSS

### 选择原因

1. **全栈能力**: API Routes 可以做 BFF 层，减少前后端交互复杂度
2. **SSR/SSG**: Dashboard 页面可以静态生成，候选人详情可以服务端渲染
3. **生态丰富**: 组件库、模板多，适合快速搭建 Demo
4. **Tailwind CSS**: 原子化 CSS，开发速度快，适合展示型项目

### 不选纯 React (Vite) 的原因
- 缺少 SSR，首屏加载慢
- 需要额外配置路由

---

## 总结: 选型核心原则

| 原则 | 说明 |
|---|---|
| **开发/生产分离** | Local 模式免费开发，Cloud 模式生产部署，同接口零切换 |
| **渐进式复杂度** | MVP 先跑通闭环，后续逐步加 RAG、工作流、评估 |
| **面试可讲解** | 每个选型都能说清楚"为什么选这个而不选那个" |
| **生产意识** | 即使是校招项目，也按生产标准选型 (PostgreSQL > SQLite, Qdrant > Chroma) |
